# Развернуть и подключить к порталу

> Last reviewed: 2026-09-25

## Как устроен выкат

Схема — как в эталоне `client-bank-alfa-by`: **GHCR + Watchtower за общим nginx-proxy** (TLS —
Let's Encrypt). Адрес приложения — **`https://invoice-from-tasks.bx-shef.by`**.

| Шаг | Что происходит |
|---|---|
| PR → `main` | `ci` (линт, тесты, типы, сборка) + `docker-build` (образ собирается, в реестр не идёт) |
| push в `main` | `ci` → `deploy`: образ `ghcr.io/bx-shef/invoice-from-tasks` с тегами `latest` и `sha-<коммит>` |
| сервер | Watchtower раз в ~5 минут видит новый `latest` и пересоздаёт контейнер; nginx-proxy выставляет его наружу по `VIRTUAL_HOST` и выпускает сертификат |

- `deploy` ждёт зелёный `ci`: красный CI до сервера не доходит.
- В GHCR пушит встроенный `GITHUB_TOKEN` (`packages: write`), отдельный секрет не нужен.
- Образ один на любой сервер: адрес и секреты он читает из окружения при запуске. Единственный
  build-arg — коммит сборки: его показывает `GET /api/health` (`commit`) и `make doctor`.
- Мерж, который меняет только документацию, тесты, смок, `Makefile` или compose-файлы, образ не
  пересобирает (`paths-ignore` в CI) — прод зря не перезапускается.
- Выкатить заново без коммита — Actions → CI → Run workflow на `main` или `make prod-redeploy` на
  сервере.

## 1. Сервер

### Один раз на хост

nginx-proxy, acme-companion и Watchtower — общие для всего сервера. Если на нём уже крутится
client-bank или currency-converter, они стоят. Проверка:

```bash
docker network ls | grep proxy-net
docker ps --format '{{.Names}}\t{{.Image}}' | grep -E 'nginx-proxy|acme-companion|watchtower'
```

Чего-то нет — поставить по разделу «Если nginx-proxy / Watchtower ещё не стоят» в
[`client-bank-alfa-by/docs/DEPLOY.md`](https://github.com/bx-shef/client-bank-alfa-by/blob/main/docs/DEPLOY.md):
сеть `proxy-net`, прокси из `currency-converter/docker-compose.nginxproxy.yml`, Watchtower с
`--label-enable`. **Второй Watchtower не поднимать**: он конфликтует по имени контейнера и
перезапускает всё дважды.

**Пакет GHCR — публичный**: как сделать — `docs/REPO_SETUP_CHECKLIST.md` §4. Тогда серверу и
Watchtower не нужен `docker login`. Оставляете приватным — на сервере `docker login ghcr.io` с
токеном `read:packages` и креды для Watchtower, как в эталоне («Если репозиторий приватный»).

**Долгие ответы BitrixGPT.** nginx-proxy ждёт ответа приложения 60 секунд, а запрос названий или
консультации с повторами может идти дольше (до 120 с на попытку, до трёх попыток —
`server/utils/llm.ts`). Иначе человек получит `504`, а запрос дойдёт до конца и потратит лимит
впустую. Таймаут для нашего домена поднимает `make proxy-timeout` — после `make prod-up`, шаг в
«Развёртывании» ниже. Цель:
- берёт домен из `VIRTUAL_HOST` работающего контейнера приложения — того, что прокси обслуживает;
- находит контейнер nginx-proxy (не нашёлся или их несколько — `make proxy-timeout PROXY=<имя>`);
- дописывает `proxy_read_timeout 400s;` в его `/etc/nginx/vhost.d/<домен>_location`, сохраняя
  другие директивы; новый файл начинает с `default_location`, если он есть;
- перестраивает конфиг прямо в прокси (`docker-gen`, `nginx -t`, reload) — приложение не
  перезапускается — и проверяет, что файл подключён. Уже настроено — ничего не делает.

Предупредит, если `vhost.d` у прокси — не отдельный том: тогда настройка пропадёт, когда прокси
пересоздадут.

### Развёртывание

**DNS A-запись `invoice-from-tasks.bx-shef.by` должна указывать на сервер до подъёма** — иначе
сертификат не выпустится. На сервере нужны только два файла из репозитория и `.env`: образ
самодостаточный.

```bash
mkdir -p /home/bitrix/invoice-from-tasks && cd /home/bitrix/invoice-from-tasks

curl -fsSL -O https://raw.githubusercontent.com/bx-shef/invoice-from-tasks/main/docker-compose.prod.yml
curl -fsSL -O https://raw.githubusercontent.com/bx-shef/invoice-from-tasks/main/Makefile

umask 077   # .env и копии тома — только владельцу
cat > .env <<EOF
DOMAIN=invoice-from-tasks.bx-shef.by
# Ваш e-mail для Let's Encrypt или пусто (адреса на example.com Let's Encrypt отвергает).
LETSENCRYPT_EMAIL=
B24_TOKEN_ENC_KEY=$(openssl rand -hex 32)
# Заполнить после раздела 2 (кабинет разработчика Маркета):
B24_CLIENT_ID=
B24_CLIENT_SECRET=
B24_APP_CODE=
# Ключ Вайбкода для BitrixGPT:
VIBE_API_KEY=
EOF
grep B24_TOKEN_ENC_KEY .env   # ⚠ сохраните ключ вне сервера (менеджер паролей)

make prod-up          # поднять контейнер (образ из GHCR)
make proxy-timeout    # таймаут прокси для BitrixGPT (см. выше); приложение не перезапускается
make ps               # через ~20 секунд — healthy
make health           # какие настройки заданы (без секретов); ключи и код — false до раздела 2
make doctor           # всё разом: контейнер, настройки, прокси, https, сертификат, Watchtower, диск
```

`make doctor` только читает. Каждая строка — ✓ или ✗, а после «→» — что делать. До раздела 2
он честно покажет ✗ «не задано в .env: B24_CLIENT_ID/B24_CLIENT_SECRET,B24_APP_CODE,…». https он
проверяет с самого сервера; если сервер не видит себя по внешнему адресу, проверьте с другого
компьютера: `curl -s https://invoice-from-tasks.bx-shef.by/api/health` — в ответе
`request.forwardedFor` должно быть `used`.

**Keepalive к прокси выключен** меткой `com.github.nginx-proxy.nginx-proxy.keepalive=disabled`.
По умолчанию nginx-proxy держит соединения с приложением открытыми до 60 секунд, а Node закрывает
простаивающие через 5. Запрос в уже закрытое соединение получает `502`, и POST nginx не повторяет, а
Битрикс24 открывает страницы приложения именно POST-ом. Замер 2026-09-25: страница установки
открылась, `/app` сразу после неё — `502`.

`make` запускает compose без `DOMAIN`, `LETSENCRYPT_EMAIL` и `B24_TOKEN_ENC_KEY` из окружения
оболочки: иначе они побеждали бы `.env`, и экспортированный домен соседнего проекта увёл бы наш
сайт на чужой адрес. Источник один — `.env`.

`docker-compose.prod.yml` сам задаёт `NUXT_PUBLIC_SITE_URL=https://<DOMAIN>` и `TRUST_PROXY=1`
(nginx-proxy дописывает адрес клиента в `X-Forwarded-For`). Токены установки лежат в томе
`portals` (`/app/.data`): Watchtower пересоздаёт контейнер на каждом выкате, том это переживает.

**Обновления.** Образ — сам, через Watchtower. Какая сборка запущена, показывает `make doctor`
(«сборка» — первые 7 знаков коммита): сравните с последним коммитом `main`. `docker-compose.prod.yml`
и `Makefile` Watchtower не трогает:
- новые цели — `make self-update`;
- новый compose — `make compose-update` покажет разницу с репозиторием, `make compose-update
  CONFIRM=1` заменит файл (копия прежнего — рядом), затем `make prod-up`.

Список целей — `make help`.

**Откат** на известную версию: в `docker-compose.prod.yml` на сервере заменить `:latest` на
`:sha-<первые 7 знаков коммита>` (так тег ставит CI; список — на странице пакета) и `make prod-up`.
Watchtower следит за тегом из файла, поэтому, пока там `sha-…`, новые выкаты не приедут; вернуть
`:latest` — вернутся. Тот же приём — **пауза автообновлений**, например на время первых недель на
рабочем портале. ⚠ `make compose-update CONFIRM=1` вернёт `:latest` — в показанной разнице это видно.

**Копия тома с токенами** — `make backup` (файл в `./backups`). Токены в ней зашифрованы
`B24_TOKEN_ENC_KEY`: без ключа копия бесполезна, поэтому ключ хранится отдельно. Восстановить:

```bash
docker compose -f docker-compose.prod.yml exec -T app tar xzf - -C /app/.data < backups/portals-<дата>.tgz
docker compose -f docker-compose.prod.yml restart app
```

Потеряли том без копии — порталам нужно переустановить приложение: без токенов установщика не
работает запись ставок редакторами-не-администраторами.

⚠ `TRUST_PROXY=1` верит `X-Forwarded-For` от любого адреса частной сети, а сеть `proxy-net` общая
для проектов хоста. Соседний контейнер на ней может назвать себя любым адресом и обойти лимиты
по IP (события установки, живые проверки фрейм-токена); лимиты BitrixGPT считаются по сотруднику и
порталу и так не обходятся. Держите на `proxy-net` только свои проекты.

### Частые сбои

Сначала — `make doctor`: он называет большинство причин ниже сам.

| Что видно | Причина | Что делать |
|---|---|---|
| `502 Bad Gateway` в окне приложения, чаще при повторном открытии | прокси держит соединения с приложением (keepalive), а Node закрывает простаивающие через 5 с; POST из портала nginx не повторяет | `make compose-update CONFIRM=1` (метка `keepalive=disabled`), `make prod-up`; в `make doctor` — ✓ «прокси ходит в приложение без keepalive» |
| `502` сразу после выката, через несколько секунд проходит | Watchtower пересоздаёт контейнер, Node ещё не слушает | подождать; повторяется — `make logs` |
| `504` или «Консультация не удалась» примерно через минуту | прокси ждёт ответа 60 с, BitrixGPT отвечает дольше | `make proxy-timeout` |
| Из портала всё отвечает `503`: BitrixGPT, настройки, ставки | не задан `B24_APP_CODE` | код — на главной приложения у администратора; в `.env`, `make prod-up` |
| Установка падает с `500` или не сохраняется | нет `B24_TOKEN_ENC_KEY` или ключей `B24_CLIENT_ID`/`B24_CLIENT_SECRET` | `make doctor` назовёт переменную; в `.env`, `make prod-up`, переустановить |
| Браузер ругается на сертификат | A-запись домена не на этот сервер, Let's Encrypt отверг e-mail или лимит выпусков | `dig +short <домен>`; `docker logs` контейнера acme-companion; `LETSENCRYPT_EMAIL` — пусто или настоящий |
| Новая версия не приехала | мерж менял только документацию, тесты или `Makefile` — образ не собирается; Watchtower не запущен; в compose пин `sha-…` | «сборка» в `make doctor` против коммита `main`; `make prod-redeploy` — не ждать Watchtower |
| Товары записаны, а в карточке счёта их не видно | карточка не перерисовывается сама: способа перерисовать её из встройки в документации мы не нашли (`BX24.reloadWindow` работает только для приложения в отдельном окне) | обновить страницу счёта (F5); сумма счёта уже пересчитана |

### Без nginx-proxy (локально или другой сервер)

`docker-compose.yml` собирает образ из исходников и публикует порт **только на
`127.0.0.1:3000`**: HTTPS и доступ снаружи даёт свой обратный прокси (nginx, Caddy, Traefik) на
этом же сервере, тогда `TRUST_PROXY=1`. Прокси на другой машине — замените на `"3000:3000"` и
закройте порт сетевым экраном: порт, доступный мимо прокси, позволяет обходить лимиты по IP.

```bash
cp .env.example .env               # заполнить (см. ниже)
docker compose up -d --build       # на сервере — в фоне
make build-local                   # локальная проверка: то же, но на переднем плане
```

Токены установки — в томе `portals` (`/app/.data`). Без тома пересоздание контейнера их потеряет,
и запись ставок не-администраторами перестанет работать до переустановки приложения на портале.

### Переменные окружения

Полный шаблон с комментариями — `.env.example`.

| Переменная | Зачем | Без неё |
|---|---|---|
| `DOMAIN` (прод) | домен для nginx-proxy и сертификата; из него `docker-compose.prod.yml` собирает `NUXT_PUBLIC_SITE_URL` | compose не поднимется |
| `NUXT_PUBLIC_SITE_URL` | адрес для обработчиков встройки и событий; в проде задаётся из `DOMAIN` | установка возьмёт адрес из браузера |
| `B24_CLIENT_ID`, `B24_CLIENT_SECRET` | сверка установки и обновление токена установщика | установка **не сохраняется** (`docs/B24_EVENTS.md`) — не работают BitrixGPT и запись ставок редакторами |
| `B24_TOKEN_ENC_KEY` | шифрование токенов установки — access и refresh (`openssl rand -hex 32`) | установка падает с `500` |
| `B24_APP_CODE` | принимать фрейм-токены только своего приложения; код показывает администратору главная страница приложения, пока переменная не задана | **`503` на все запросы из фрейма**: BitrixGPT, сохранение настроек и ставок |
| `TRUST_PROXY` | `1` — сервер за обратным прокси: лимиты считаются по IP клиента; в проде уже `1` | лимиты по IP общие для всех, кто за прокси (адрес прокси один) |
| `VIBE_API_KEY` или `BITRIXGPT_API_KEY` | BitrixGPT (ключ Вайбкода `vibe_…`) | режим названий «BitrixGPT» и консультации отвечают ошибкой |
| `B24_APPLICATION_TOKEN` | фиксированный `application_token`; для приложения из Маркета — **пустой** (у каждого портала свой) | первый `ONAPPINSTALL` задаёт токен портала |
| `B24_SELFHOSTED_HOSTS` | коробочные порталы вне `*.bitrix24.*` для SSRF-гарда | к ним сервер не пойдёт; ⚠ установка из коробки всё равно не сохраняется — приложение облачное (`docs/B24_EVENTS.md`) |

⚠ **Копия `B24_TOKEN_ENC_KEY` — вне сервера** (менеджер паролей, хранилище секретов). Потеря или
смена ключа делает сохранённые токены нечитаемыми: запись ставок редакторами перестанет работать
на всех порталах до переустановки приложения. Ротации ключа пока нет (`server/utils/secretCrypto.ts`).

### Пределы запросов

`server/middleware/requestLimits.ts`, значения — `server/utils/requestLimits.ts`:
- тело POST к `/api`: события портала — до 64 КБ, остальное — до 512 КБ; больше — `413`;
- без заголовка `Content-Length` — `411` (тело неизвестной длины пришлось бы читать целиком).
  Браузер и портал его шлют; ⚠ для событий портала это проверяется после выката
  (`docs/project-map.md`);
- события установки и удаления — до 60 в минуту с одного адреса (IPv6 — с сети /64), `429`;
  прочие события не считаются: они ничего не стоят, а иначе чужой портал мог бы выжечь лимит и
  заблокировать чужие установки;
- сверки установки — до 600 в минуту всего: каждая — исходящий запрос к серверу авторизации с
  нашими `client_id`/`client_secret`; мусор и удаления этот потолок не тратят;
- живые проверки фрейм-токена — до 60 в минуту с одного адреса (IPv6 — с /64), `429`;
- BitrixGPT — в двух измерениях: 120 запросов и 3000 строк счёта за 10 минут на сотрудника,
  1200 запросов и 30 000 строк за час на портал; консультация весит 25 строк
  (`server/utils/rateLimit.ts`).

HTTPS обычно даёт обратный прокси перед контейнером — тогда `TRUST_PROXY=1`, иначе все запросы
выглядят пришедшими с адреса прокси. Берётся **последний** адрес `X-Forwarded-For` (его дописывает
прокси), поэтому схема рассчитана на один прокси. Заголовку верим, только если соединение пришло
из частной сети (свой прокси, мост Docker): клиент из интернета подставить себе адрес не сможет.
Проверка: `curl -s https://<адрес>/api/health` через прокси — в ответе `request.forwardedFor`
должно быть `used`; `ignored` — заголовку не верим (нет `TRUST_PROXY=1` или прокси ходит к
приложению не из частной сети), и все клиенты делят лимиты адреса прокси.

## 2. Приложение в Маркете

Приложение регистрирует владелец в кабинете разработчика Битрикс24 Маркетплейс и ставит на
тестовый портал кнопкой «Протестировать» — до модерации и публикации. Порядок — по статье
документации «Как добавить решение в кабинет разработчика» и «Мастер установки тиражного
приложения» (MCP `b24-dev-mcp`):

1. «Мои приложения» → «Добавить приложение» → регион → «Создать».
2. Технические характеристики:

   | Поле | Значение |
   |---|---|
   | Разделы системы (скоупы) | `crm`, `task`, `catalog`, `user_brief`, `placement` |
   | Добавлять свою страницу и пункт в главном меню | да — у приложения есть главная `/app` |
   | Встраивать виджеты в интерфейс | да — кнопка «Заполнить из задач» в карточке счёта |
   | Может устанавливать любой пользователь | нет — ставит администратор |
   | Тип приложения, минимальный тариф | на ваше усмотрение: приложению нужны CRM со счетами, задачи с учётом времени и REST |
   | Ссылка на приложение | `https://invoice-from-tasks.bx-shef.by/app` |
   | Ссылка на установочное приложение | `https://invoice-from-tasks.bx-shef.by/install` |

   ⚠ Право задач — **`task`** (не `tasks`): так его принимает портал (`docs/REST_METHODS.md`).
   Названия полей — из документации; в кабинете формулировки могут чуть отличаться.
3. **Код приложения** — вверху справа в карточке: `<код партнёра>.<код>`. Вторую часть можно
   менять только до первой положительной модерации. Это `B24_APP_CODE`.
4. **«Протестировать»**: там ключи `client_id` и `secret_id` — это `B24_CLIENT_ID` и
   `B24_CLIENT_SECRET`, и поле адреса портала — **тестовый портал**. Откроется карточка решения
   на портале с кнопкой «Установить».
5. Ключи и код — в `.env` на сервере, затем `make prod-up` (контейнер пересоздастся с ними).
   `B24_APPLICATION_TOKEN` не задавать.

Установку, удаление и переустановку проверяем сами — этого требует и модерация.

Пока `B24_APP_CODE` не задан, главная страница приложения (`/app`) показывает администратору
портала код из `app.info` и список того, что не настроено на сервере (по `GET /api/health`). До
этого BitrixGPT, настройки и ставки отвечают `503`.

### Без Маркета: локальное приложение своего портала

В карточке локального приложения: «Путь обработчика» — `https://<адрес>/app`, «Путь для
первоначальной установки» — `https://<адрес>/install` (название поля — из статьи «Мастер установки
локального приложения»), те же права, режим «только API» выключен. Ключи `client_id` и
`client_secret` портал выдаст после сохранения.

## 3. Установка и первая настройка

1. Установить приложение (кабинет Маркета → «Протестировать» → «Установить» на тестовом портале) —
   откроется `/install`: проверит права, зарегистрирует пункт
   «Заполнить из задач» в карточке счёта, подпишется на события, завершит установку. Недостающие
   права покажет списком.
2. Проверить, что сервер готов: `GET /api/health` → все флаги `config` (кроме `trustProxy`
   без прокси) — `true`. Порталы он не показывает; что установка дошла, видно по тому, что
   `/api/rates` и BitrixGPT перестали отвечать `409 portal not installed`.
3. Администратор: «Приложения» → «Счёт из задач» → «Настройки»:
   - «Хранилище» → «Замерить предел» (**на тестовом портале**, `docs/SETTINGS.md`);
   - «Общие» → валюта ставок, округление (шаг и направление), режим названий;
   - «Ставки», «Наценки» (на всё и правила по тегам задач), «Промпты», «Доступ».
4. Открыть счёт → верхняя кнопка карточки → «Заполнить из задач» → «Собрать строки» → «Заменить»
   или «Добавить». После записи обновите страницу счёта (F5): карточка сама не перерисовывается.
   Единицу измерения строк («час») задайте в «Общих» заранее — иначе портал подставит свою
   («штука» на тестовом портале, 2026-09-25). REST и расчёт до установки
   проверяет `pnpm smoke` (`docs/SMOKE.md`); установка добавляет то, что видно только из
   приложения. На тестовом портале заодно проверить:
   - задача с тегом из правил получает его наценку (в предпросмотре — `N% (#тег)`);
   - счёт в валюте, отличной от валюты ставок, — цены пересчитаны, предупреждение о курсе есть
     и в предпросмотре, и после записи; валюта без курса — остановка с понятным текстом.

## Смена адреса сервера

Переустановите приложение (или откройте `/install` из портала): установка снимет встройку и
подписки на события со старым адресом (`placement.unbind`, `event.unbind`) и зарегистрирует новые.
Если приложение уже установлено, `installFinish` не вызывается — страница только обновит
встройку и подписки.
