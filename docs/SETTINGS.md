# Настройки приложения

> Last reviewed: 2026-09-24

Где лежат настройки, кто их меняет и сколько их влезает. Код формата —
`shared/domain/settings.ts` и `shared/domain/rates.ts`, бюджет места — `shared/domain/storageBudget.ts`.

## Где хранятся

В **настройках приложения на портале** (`app.option`), а не на нашем сервере: у каждого портала
свои, переустановка сервера их не трогает. Ключи:

| Ключ | Что | Кто пишет |
|---|---|---|
| `ift_settings_v1` | общие настройки, одна JSON-строка | администратор портала (через `/api/settings`) |
| `ift_rates_v1` | ставки часа, компактный JSON `[[userId, ставка, "ГГГГ-ММ-ДД", productId?], …]` | администратор или назначенный редактор (через `/api/rates`) |
| `ift_storage_v1` | результат замера предела места `{"limit": байт, "at": "ГГГГ-ММ-ДД"}` | администратор (раздел «Хранилище») |
| `ift_probe_tmp` | пробные данные замера; после замера — пустая строка | замер |

Суффикс `_v1` — версия формата. Несовместимая смена формата = новый ключ и BREAKING CHANGE в
squash-сообщении (`docs/AGENT_RULES.md` §4.2): уже настроенные порталы иначе потеряют настройки.

Разбор при чтении — **защитный** (`parseSettings`, `parseRates`): хранилище — внешние данные,
битое поле заменяется умолчанием, лишние ключи (включая `__proto__`) отбрасываются. Запись —
через тот же разбор: в хранилище не попадает ничего, чего нет в формате.

## Общие настройки (`ift_settings_v1`)

| Поле | Что | По умолчанию |
|---|---|---|
| `rounding` | шаг округления, минут: `0` (как есть), `60`, `30`, `10`, `5` | `0` |
| `currency` | валюта ставок (код ISO из `crm.currency.list`) | пусто → заполнять нельзя |
| `rateEditors` | ID сотрудников, которым разрешено менять ставки (кроме администраторов) | `[]` |
| `markup.defaultPercent` | наценка «на всё», % | `0` |
| `markup.sections` | `[{id, name, percent}]` — наценки по папкам каталога | `[]` |
| `markup.products` | `[{id, name, percent}]` — наценки по товарам | `[]` |
| `defaultProductId` | товар каталога для строк по умолчанию | `null` |
| `measureCode` | код единицы измерения строк | `null` — портал выберет сам |
| `naming` | `plain` (как есть) или `ai` (BitrixGPT) | `plain` |
| `prompts.taskTitle`, `prompts.timeBlock` | свои промпты названий; `null` — системный | `null` |
| `consultPrompts` | `[{id, title, text}]` — промпты консультаций (до 20) | `[]` |

## Ставки (`ift_rates_v1`)

«Сотрудник — ставка — начиная с даты» (+ необязательный товар каталога — см.
`docs/PROCESSING.md` §5). Ставка действует с даты до следующей версии того же сотрудника.
Хранятся кортежами без имён полей — ради места.

## Кто что может менять

| Что | Кто | Где проверяется |
|---|---|---|
| Читать настройки и ставки | любой сотрудник портала | портал (`app.option.get` доступен всем) |
| Общие настройки | администратор портала | сервер: `profile.ADMIN` фрейм-токена |
| Ставки | администратор **или** сотрудник из `rateEditors` | сервер: `profile` + список из настроек портала |
| Замер места | администратор | портал (`app.option.set` только ему) |

⚠ **Почему ставки пишет сервер.** `app.option.set` доступен **только администратору**
(документация метода: «Administrator authorization required»). Назначенный редактор ставок не
администратор — его токеном записать нельзя. Поэтому `/api/rates` проверяет, кто пришёл,
**сам читает** список редакторов из настроек портала (не из запроса — его подделать легко) и
пишет **токеном администратора, установившего приложение** (сохраняется при установке —
`docs/B24_EVENTS.md`). Администратор пишет своим токеном.

Решение «кто и каким токеном» — `server/utils/optionWrites.ts` (покрыто тестом
`tests/server/optionWrites.test.ts`). Ответы `/api/settings` и `/api/rates`: `403` — нет прав,
`400` — тело не того вида, `422` — ошибки в строках ставок (списком, для подсветки), `413` — не
влезает в бюджет места (с расчётом `usage`). Запросы из фрейма без `B24_APP_CODE` на сервере —
`503` (`docs/DEPLOY.md`).

## Сколько влезет

ТЗ: «ограничение на место есть — нужно уточнить, сколько влезет, и ограничить (−30 % запаса)».

**Что нашли (2026-09-24):**

- Документация REST (`app.option.set`, MCP `b24-dev-mcp`) размер **не называет**.
- Документация ядра `\Bitrix\Main\Config\Option::set` (с версии 12.0.7) говорит дословно:
  «Максимальная сохраняемая длина значения — 2000 символов»
  ([training.bitrix24.com](https://training.bitrix24.com/api_d7/bitrix/main/config/option/set.php)).
- **Гипотеза, не замер:** опции приложения хранятся через `Option::set` **одним**
  сериализованным значением на все ключи. Тогда предел общий для настроек и ставок.
- Ни в документации, ни в эталонах нет живого замера. Документация ядра старая и может не
  отражать нынешнюю схему базы.

**Почему нельзя просто «записать побольше и посмотреть».** Если хранилище молча обрезает
значение, обрезанная PHP-сериализация не читается целиком — портал теряет **все** настройки
приложения, а не только лишнее.

**Что сделано:**

1. Пока предел не замерен, бюджет считается от **документированных 2000** символов:
   `2000 × 0,7 = 1400` байт на все опции вместе. Это консервативно: хватит на базовые настройки и
   около 30–40 ставок, но не на длинные свои промпты.
2. В настройках есть вкладка **«Хранилище»** с кнопкой **«Замерить предел»** (только
   администратор). Замер (`app/utils/storageProbe.ts`):
   - снимает копию всех опций;
   - пишет пробный ключ так, чтобы все опции заняли очередную ступень
     (`PROBE_LADDER`, байт: 1 500 · 1 990 · 2 010 · 4 000 · 8 000 · 16 000 · 32 000 · 60 000 ·
     65 000 · 66 000 · 131 000 · 262 144 — последняя ступень ровно 256 КиБ);
   - после каждой записи читает всё обратно и сверяет: пробный ключ цел, остальные не тронуты;
   - на первой неудаче останавливается; если что-то испортилось — возвращает копию;
   - сохраняет последнюю удачную ступень в `ift_storage_v1`.
3. Дальше бюджет везде (страница, `/api/settings`, `/api/rates`) считается от замера минус 30 %.
   Размер оценивается по длине PHP-сериализации в байтах UTF-8 — кириллица занимает 2 байта, так
   что оценка не занижает.

**Порядок для владельца:** установить приложение на **тестовый** портал → Настройки →
«Хранилище» → «Замерить предел» → результат записать в `docs/project-map.md` и в этот раздел.
Если на облаке предел окажется большим, стоит обсудить, поднимать ли документированное
умолчание для новых порталов.

Поведение замера на обоих вариантах отказа (ошибка записи и тихая порча всех опций) проверено
тестом на имитации портала: `tests/storageProbe.test.ts`.

## Известные ограничения (приняты осознанно)

- **Гонка «прочитал — записал».** Сервер считает бюджет по всем опциям, прочитанным перед
  записью, и пишет один ключ. Если два администратора сохраняют разные разделы в одну и ту же
  секунду, сумма может превысить бюджет. Защищает запас 30 %: бюджет — не предел, а 70 % от
  него. Блокировки на стороне портала нет, а своя на сервере не спасла бы от записи из другого
  окна портала напрямую.
- **Замер во время работы.** Замер пишет пробный ключ; сохранение настроек в эту же минуту
  увидит его в подсчёте и может получить `413`. Замер — разовая операция администратора на
  тестовом портале, поэтому отдельной блокировки нет.
